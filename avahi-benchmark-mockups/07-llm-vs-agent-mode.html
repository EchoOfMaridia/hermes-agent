LLM Mode vs Agent Mode

Per General Concepts: both modes are first-class. Every benchmark exposes a hookable connector. Standardized env-var / arg config. Stock LLM test = LLM mode. External framework challenge = agent mode.
LLM Mode
STOCK LLM · MINIMAL HARNESS
DEFAULT

The benchmark provides a basic harness loop. The LLM is given tools, a rolling context, and minimal hints. No agent framework. The point is to test what stock LLMs can do on their own with the smallest possible harness around them.

Context window
128K default (rolling, truncate from top)
Tools
Benchmark + harness tools (write_to_scratchpad, etc.)
Sub-agents
Benchmark provides list_sub_agents, call_sub_agent
Hints
Benchmark sends reminders on stall. Minimal strategy hints.
Token budgeting
TPipe-style rolling window when agent is TPipe
Memory
None between runs. All state lives in the scratchpad.
Best for
Benchmarking the model itself. Standardized "what can the LLM do."
Agent Mode
EXTERNAL FRAMEWORK · FULL OWNERSHIP
CHALLENGE

The agent developer brings their own framework. The benchmark is just a tool provider. No hints. The agent must know the rules, manage its own memory, design its own sub-agents, and call the right tools at the right time.

Context window
Agent's problem. No benchmark ceiling.
Tools
Only the benchmark's mandatory + optional tools. No harness extras.
Sub-agents
None provided. Agent brings its own.
Hints
None. The benchmark is silent except for events.
Token budgeting
Agent's problem. No benchmark enforcement.
Memory
Agent's problem. The benchmark doesn't help.
Best for
Head-to-head: "can your framework beat ours on our own benchmark?"

Connector Spec — How External Frameworks Connect

Per General Concepts: "Standardized means of connecting and exchanging data. This includes parameters being configurable as env vars or program arguments as well."

Environment Variables

# Required
export TTT_BENCHMARK="butter|drivethru|openvend"
export TTT_MODE="llm|agent"
export TTT_MODEL="MiniMax-M2.5"      # or vendor/model slug
export TTT_SEED="1723"               # omit for random
export TTT_RUN_ID="my_framework_v3.1_seed1723_run1"

# Optional — benchmark-specific
export TTT_MAX_TURNS="500"            # override cap
export TTT_MAX_ERRORS="5"            # override retry cap
export TTT_DAYS="28"                  # Open-Vend only
export TTT_HOURS_PER_DAY="12"         # Open-Vend only
export TTT_STARTING_BANK="500"       # Open-Vend only
export TTT_CONTEXT_WINDOW="128000"    # LLM mode only
export TTT_VENDOR_MIX="control|hostile|scammer|random"

# Output
export TTT_TRACE_OUT="./trace.jsonl"   # event stream
export TTT_REPORT_OUT="./report.json"  # final score + breakdown

Connector protocol (agent mode)

The agent framework connects via one of two surfaces. The benchmark emits events; the agent emits tool calls.

Surface A: stdio JSON-RPC

// Inbound (benchmark → agent)
{
  "jsonrpc": "2.0",
  "method": "event",
  "params": {
    "type": "CASE_START",
    "case_id": "5",
    "category": "jailbreak",
    "customer_line": "..."
  }
}

// Outbound (agent → benchmark)
{
  "jsonrpc": "2.0",
  "method": "tool_call",
  "params": {
    "tool": "submit_order",
    "args": {"items": [...]}
  }
}

Surface B: HTTP/WS

# Endpoints
POST /v1/connect          # handshake, return run_id
GET  /v1/events          # SSE stream of benchmark events
POST /v1/tool_calls      # agent tool calls
GET  /v1/score           # current score + breakdown
WS   /v1/stream          # full duplex (events + calls)

# Auth
Authorization: Bearer <ttt_run_token>

# Rate limit
"X-RateLimit-Limit": "120/min"
"X-RateLimit-Remaining": "118"
FOR AVAHI The connector has to be generic enough that any framework can plug in without bespoke integration. Two surfaces (stdio JSON-RPC for shell-friendly harnesses, HTTP/WS for everything else). Token auth so the benchmark can rate-limit and attribute runs. Both surfaces emit the same event schema from page 4. Avahi should ship an SDK in at least Python and TypeScript on day one; without an SDK, only the largest agent framework teams will attempt the challenge.

FOR AVAHI The "PROVIDED" tag in LLM mode means the benchmark auto-injects the tool into the model's function-calling schema. The "OPTIONAL" tag in agent mode means the benchmark exposes the tool as a callable but does not auto-inject — the agent framework decides whether to surface it. The "UNAVAILABLE" cells (list_sub_agents, call_sub_agent in Open-Vend agent mode) are explicit per the spec: "Not applicable to agent mode where the agent developer/framework is expected to handle and design its own sub agents." This table needs to be the source of truth for the SDK generation.
